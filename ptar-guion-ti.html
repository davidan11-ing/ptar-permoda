Cómo está construida

La aplicación tiene tres capas. La primera es lo que ve el usuario en el navegador: la interfaz, los formularios, los gráficos. La segunda es el motor que corre en el servidor y procesa toda la lógica: los cálculos, las reglas de negocio, la seguridad. La tercera es la base de datos donde viven los registros.

La interfaz está hecha en React con TypeScript — son los lenguajes que el navegador interpreta para mostrar la pantalla al usuario. El motor del servidor está escrito en C# sobre .NET 10, que es el entorno de ejecución de Microsoft para aplicaciones empresariales. La base de datos es MySQL, un motor relacional maduro, gratuito y de código abierto con más de 25 años en el mercado.

En términos prácticos de despliegue: los tres componentes corren en el mismo computador o servidor. El motor de la aplicación escucha en el puerto 8001 de esa máquina — un puerto es simplemente un canal de comunicación numerado dentro del mismo equipo, como una extensión telefónica. La base de datos escucha en el puerto 3306. El navegador del usuario se conecta a esa máquina y el motor le responde. La base de datos nunca queda expuesta directamente hacia afuera — solo el motor puede hablarle, y lo hace internamente dentro del mismo equipo.

Quién puede hacer qué

El sistema maneja tres perfiles de usuario con permisos distintos.

El Operario es quien trabaja en el turno. Solo puede ingresar datos de su turno: las lecturas de los medidores de caudal, el consumo de reactivos químicos, las muestras de calidad del agua y las condiciones de operación de los equipos. No puede ver los dashboards de análisis ni editar lo que otros registraron.

El Encargado es el supervisor. Tiene acceso completo: puede registrar igual que el operario, ver todos los paneles de análisis, corregir registros, configurar qué información ve la gerencia y generar los informes en PDF.

El Administrador es el perfil para gerencia o visualizadores. Solo puede ver — no editar ni registrar. Ve exactamente lo que el Encargado decidió mostrarle: un panel consolidado que el supervisor arma y congela con los datos que considera relevantes.

Estos permisos se aplican tanto en la interfaz como en el servidor. Si alguien intenta acceder a una función que no le corresponde por el lado técnico, el servidor lo rechaza independientemente de lo que muestre la pantalla.

Cómo fluyen los datos

El operario llena su formulario de turno y lo envía. El servidor valida que los datos sean coherentes — rangos correctos, formatos válidos, que correspondan al turno activo — y los guarda en la base de datos. Si el operario envía el mismo turno dos veces por error, el sistema actualiza el registro existente en lugar de crear un duplicado.

Los dashboards no consultan los registros crudos directamente. La base de datos tiene vistas analíticas pre-armadas — cálculos de balance hídrico, estadísticas de calidad, costos de reactivos — que el servidor consulta para alimentar los gráficos. Esto hace que los dashboards respondan rápido incluso con meses de datos acumulados.

Cuando el Encargado genera un informe, el servidor arma el documento directamente — sin depender de Excel ni de herramientas externas — y lo entrega como PDF listo para imprimir o enviar.

Cómo protegemos el sistema

Cuando un usuario hace login, el servidor verifica sus credenciales. Las contraseñas nunca se guardan legibles en la base de datos — se guardan transformadas de forma irreversible, de modo que ni el equipo de desarrollo puede recuperarlas. Si alguien accede físicamente a la base de datos, no ve contraseñas.

Una vez que el login es exitoso, el servidor emite un carnet digital de sesión que dura 8 horas. Ese carnet viaja dentro de una cookie que el navegador maneja internamente — ningún script externo ni extensión del navegador puede leerlo ni robarlo. El navegador lo adjunta solo en cada petición al servidor.

Si alguien falla el login repetidas veces, la cuenta se bloquea temporalmente. Y el servidor limita cuántos intentos de login puede hacer una misma dirección de red por minuto, para dificultar ataques automáticos.

Toda la comunicación entre el navegador y el servidor viaja cifrada. Nadie en la red puede interceptar los datos mientras están en tránsito. En producción, el servidor rechaza cualquier conexión que no use el canal cifrado.

El servidor también le indica al navegador, en cada respuesta, que la aplicación no puede ser incrustada dentro de otra página web — lo que evita que alguien ponga la app dentro de una página falsa para engañar a los usuarios.

Las credenciales de la base de datos y la clave con la que firmamos los carnets de sesión viven únicamente en el servidor, en un archivo de configuración que nunca sale de allí. No están en ningún lugar accesible para quien no tenga acceso físico o remoto al servidor.

Por último, cada operación que modifica datos queda registrada automáticamente: quién la hizo, desde qué dirección de red, qué cambió y si fue exitosa. Esto permite trazabilidad completa de cualquier modificación en cualquier momento.

Qué necesita para correr

El sistema necesita un servidor con tres componentes activos: el motor de la aplicación corriendo en el puerto 8001, la base de datos MySQL corriendo en el puerto 3306, y un servidor web delante que reciba las peticiones del exterior y las pase al motor — ese servidor web puede ser IIS, que ya hace parte de Windows Server, o cualquier alternativa equivalente.

La base de datos puede vivir en el mismo servidor que el motor de la aplicación. Para el volumen de datos que maneja la planta, no se justifica infraestructura separada. Con 2 GB de RAM disponibles para el proceso del motor es más que suficiente.

Las tablas de la base de datos se crean y actualizan automáticamente cada vez que el motor arranca. No hay scripts de instalación manuales que ejecutar.

El frontend — lo que ve el usuario en el navegador — es un conjunto de archivos estáticos que puede servirse desde el mismo servidor web o desde una plataforma de hosting externo. En cualquier caso, el usuario solo necesita un navegador actualizado para usar la aplicación.

Cierre

Para resumir: la aplicación centraliza el registro y análisis operativo de la planta sobre tecnologías empresariales estándar y probadas. El acceso está controlado por roles bien definidos que el servidor aplica independientemente de la interfaz. Los datos en tránsito van cifrados. Las contraseñas no son recuperables. Las operaciones quedan trazadas. Y los requerimientos de infraestructura son modestos — un servidor con los tres componentes corriendo es todo lo que se necesita.
