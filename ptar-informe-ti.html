📋 ¿Qué es y qué hace la app?

App PTAR es una aplicación web interna de PERMODA para el monitoreo, registro y análisis operativo de la planta de tratamiento de aguas residuales. Reemplaza registros en papel y hojas de cálculo aisladas con una plataforma centralizada que permite:

Operario (turno)
  • Registro de caudales (medidores F-01)
  • Registro de reactivos químicos (F-02)
  • Muestras de calidad del agua (F-03)
  • Condiciones operativas (MBR, RO, PTAP)
  • Incidencias de turno
Encargado / Supervisor
  • Dashboard KPI en tiempo real
  • Dashboard Calidad del Agua
  • Balance Hídrico por turno/día/semana
  • Costos de reactivos químicos
  • Generación de informes PDF
Administrador / Visualizador
  • Panel configurable (selección de secciones)
  • Dashboard de mantenimientos (SharePoint)
  • Vista consolidada sin edición
  • Acceso a todos los informes
  • Explorador de tablas de la BD

🔐 Modelo de seguridad
🍪
Autenticación por Cookie httpOnly (JWT)
Al hacer login, el servidor emite un JWT firmado con HS256 (clave mínimo 32 chars, solo en appsettings.Local.json que está en .gitignore) y lo coloca en una cookie httpOnly. El token jamás toca JavaScript — el browser lo adjunta automáticamente en cada request. Expiración: 8 horas. El frontend guarda en localStorage solo datos no sensibles (nombre, rol) para mostrar en UI.
🔄
Refresh tokens con revocación
Los refresh tokens se almacenan en la tabla ptar_refresh_tokens como hashes SHA-256. Cuando el access token expira (8h), el frontend intenta un refresh silencioso una sola vez. Si falla, despacha un evento global ptar:unauthorized y limpia la sesión. Los tokens expirados son depurados por un Background Service (TokenCleanupService) que corre periódicamente.
🔒
Bloqueo de cuenta
Después de intentos fallidos de login, la cuenta se bloquea temporalmente (locked_until en ptar_users). El endpoint de login está rate-limited a 10 req/min. El endpoint de cambio de contraseña está limitado a 5 req/min.
🌐
CORS estricto por origen
Solo se permiten peticiones de http://localhost:5174 y https://ptar-app.vercel.app. AllowCredentials habilitado (requerido para la cookie). AllowedHosts en appsettings: solo localhost y 127.0.0.1, diseñado para operar detrás de un reverse proxy que maneje el dominio externo.
🛡
Security Headers
El backend inyecta en cada respuesta: X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, X-XSS-Protection: 1; mode=block, Permissions-Policy: camera=(), microphone=(), geolocation=(), Content-Security-Policy: default-src 'none'; frame-ancestors 'none'. En producción también: HSTS y redirect HTTPS.
💉
Prevención de SQL Injection
Todas las queries usan Dapper con DynamicParameters (queries parametrizadas — nunca concatenación de strings de usuario). Los nombres de columnas y tablas dinámicos en el explorador de analista se validan contra information_schema antes de incluirlos. Los límites de paginación se clampean con Math.Clamp(). INSERT/UPDATE usa el patrón ON DUPLICATE KEY UPDATE para idempotencia.
📝
Audit Log de operaciones
Un middleware intercepta todas las operaciones POST / PUT / DELETE / PATCH y registra post-respuesta: ID de usuario, rol, ruta, código HTTP y dirección IP del cliente. Permite trazabilidad de quién hizo qué y cuándo.
🚨
Manejo de errores sin exposición de stack
GlobalExceptionMiddleware es el primer middleware en el pipeline; captura cualquier excepción no manejada y responde con {"detail": "Error interno del servidor"} (HTTP 500) sin exponer stack traces, nombres de archivo ni detalles de la BD al cliente.

🔄 Flujo de datos — ciclo típico
1
Operario registra turnoLlena los formularios en el browser. Al guardar, el frontend hace POST /api/caudales/batch, /api/reactivos/batch, /api/calidad/batch con la cookie httpOnly adjunta automáticamente.
2
Backend valida y persisteEl controller valida los datos (annotations + lógica), ejecuta un INSERT con ON DUPLICATE KEY UPDATE (idempotente — re-enviar el mismo turno actualiza sin duplicar). Se recalculan campos derivados (ej: costo_quimica_turno, pesos_por_m3) dentro de la misma transacción. El audit log registra la operación.
3
Vistas MySQL consolidan los datosVistas como v_balance_hidrico, v_calidad_estadisticas, v_consumo_quimico_diario agregan y calculan métricas sobre los datos crudos. Esta lógica vive en la BD, no en el backend C#.
4
Encargado consulta dashboardsLos dashboards hacen GET a endpoints que consultan las vistas. Granularidad (turno / día / semana / mes) y rango de fechas son parámetros que se pasan como query params. El frontend renderiza gráficas (Recharts), KPIs y tablas.
5
Generación de informesEl Encargado abre el modal de informe y solicita PDF. El backend ejecuta queries analíticas, instancia plantillas QuestPDF y retorna el binario PDF (o HTML para imprimir). El browser descarga o abre el archivo.
6
Administrador visualiza panelEl Encargado configura qué secciones aparecen en el AdminDashboard (guardado en dashboard_config — tabla singleton con id=1). El Administrador accede a /admin/dashboard y ve exactamente las secciones activadas, con los filtros congelados al momento de configuración.
7
Sync mantenimientos SharePointUn Background Service (.NET IHostedService) se despierta cada 1 hora, autentica con OAuth2 contra Microsoft 365 (permodaco.sharepoint.com/sites/CONFIABILIDAD), obtiene la lista de documentos de mantenimiento y los guarda en la BD. El token OAuth se cachea en disco (gitignored).

⚠ Hallazgos de seguridad — Acción requerida
La revisión de seguridad automatizada identificó 2 vulnerabilidades de severidad ALTA en el módulo de analítica (AnalisisController.cs). Ambas están limitadas al rol encargado y administrador, pero deben corregirse antes de ampliar el acceso o desplegar en producción expuesta.
HIGH Control de acceso roto — Escalada de privilegios via PATCH genérico

Archivo: AnalisisController.cs · endpoint PATCH /api/analisis/tabla/{nombre}/{id}

El endpoint acepta cualquier nombre de tabla de la URL y actualiza columnas arbitrarias. Solo valida que la tabla exista en information_schema (base tables) y que las columnas existan — pero no tiene allowlist de tablas permitidas. Las tablas de seguridad ptar_users y ptar_refresh_tokens son base tables visibles en la misma BD.

Escenario de explotación: Un usuario encargado puede enviar PATCH /api/analisis/tabla/ptar_users/2 con body {"rol": "administrador"} para ascenderse a administrador. También puede modificar password_hash para tomar control de cualquier cuenta, o reactivar tokens revocados en ptar_refresh_tokens.

Corrección recomendada

Añadir en AnalisisController.cs un HashSet<string> TablasBloqueadas con "ptar_users" y "ptar_refresh_tokens" y retornar Forbid() al inicio de UpdateFila si el nombre de tabla está en ese set. El mismo patrón que ya existe para las vistas en VistasMeta.

HIGH Exposición de datos sensibles — Lectura de tablas de seguridad sin restricción

Archivo: AnalisisController.cs · endpoints GET /api/analisis/tablas y GET /api/analisis/tabla/{nombre}

El endpoint /api/analisis/tablas enumera todas las tablas base de la BD incluyendo ptar_users y ptar_refresh_tokens. El endpoint /api/analisis/tabla/ptar_users ejecuta SELECT * FROM ptar_users sin filtro de columnas — devuelve password_hash, rol, activo, failed_attempts, locked_until de todos los usuarios.

Escenario de explotación: Un encargado obtiene todos los hashes bcrypt. Aunque bcrypt es resistente, contraseñas débiles o comunes pueden romperse offline. Independientemente, el directorio completo de usuarios, roles y estados de cuenta queda expuesto, facilitando ataques dirigidos a cuentas de administrador.

Corrección recomendada

Aplicar el mismo TablasBloqueadas en GetTablas (filtrar de la lista retornada) y en GetTabla (retornar 404 si el nombre está bloqueado). Adicionalmente, considerar no exponer la enumeración completa de tablas a usuarios no-administradores.

⚡ Eficiencia del código — puntos relevantes para TI
🔁
Upsert idempotente en todos los batch endpoints
Los operarios pueden re-enviar el mismo formulario de turno sin crear duplicados — el patrón ON DUPLICATE KEY UPDATE en MySQL garantiza exactamente un registro por (fecha, turno, sistema).
🧠
Refresh interceptor singleton en frontend
Si múltiples llamadas API retornan 401 simultáneamente, solo se emite un request de refresh. Las demás esperan la misma Promise y reintentan en orden — evita race conditions de sesión.
📐
Lógica analítica en vistas MySQL
Los cálculos de balance hídrico, eficiencias de remoción y estadísticas de calidad viven en vistas de MySQL, no en código C#. Esto simplifica el backend y permite optimizar queries en la BD.
📦
Lazy loading por ruta en React
Cada feature se carga bajo demanda (React.lazy + Suspense). Un operario solo descarga el bundle de formularios; un encargado carga dashboards solo cuando los visita. Mejora el tiempo de carga inicial.
🔒
Límites de resultados SQL en todos los endpoints
Todos los GET tienen Math.Clamp(limit, 1, 5000) — ninguna query puede retornar filas ilimitadas. El explorador analítico tiene un límite superior de 50.000. Los batch POST tienen límite de 1 MB en el body.
🔀
Recálculo automático dentro de transacciones
Al insertar reactivos, el backend recalcula costo_quimica_turno y pesos_por_m3 dentro de la misma transacción SQL — sin jobs externos ni triggers de BD que puedan quedar inconsistentes.
