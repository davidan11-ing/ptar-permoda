1 · Carga inicial
Vite sirve index.html → carga main.tsx → monta <App/> dentro de <StrictMode>. AuthProvider comprueba si ya hay sesión activa consultando GET /auth/me con la cookie httpOnly.
2 · Autenticación
Si no hay sesión → redirige a /login. El usuario ingresa credenciales → ptarClient.ts llama POST /auth/login → el backend devuelve JWT + refresh token como cookies httpOnly. El contexto AuthContext guarda el objeto user (email, rol) en memoria.
3 · Rutas protegidas
React Router verifica AuthContext.user. Si está vacío → <Navigate to="/login">. Cada feature (calidad, caudales, reactivos…) vive en su propia ruta y carga su propio conjunto de hooks y componentes de forma lazy.
4 · Fetch al backend
Toda comunicación pasa por ptarClient.ts (capa única). Cada llamada incluye credentials:'include' para enviar la cookie JWT. Si el backend responde 401 el cliente intenta un POST /auth/refresh automático antes de forzar logout.
5 · Granularidad y render
El hook useGranularidad controla el rango temporal activo (turno/día/semana/mes). Cada dashboard lo consume y reenvía el parámetro al endpoint correspondiente. Los datos se mapean a los componentes de Recharts (gráficas, donut, tablas).
6 · Polling cada 15 s
WebSockets bloqueados por Zscaler → solución: setInterval de 15 s en cada dashboard activo que re-llama el endpoint. Al cambiar de ruta el intervalo se limpia con el cleanup de useEffect para evitar fugas de memoria.
🔄 Cómo se manejan los datos
Sin caché centralizada
No usa React Query ni Redux. Cada hook (useCaudales, useCalidad…) administra su propio estado local con useState + useEffect. El dato fresco viene siempre del backend cada 15 s.
Estado de autenticación global
AuthContext es el único estado global. Provee user, login(), logout() a toda la app. Al hacer logout llama POST /auth/logout para invalidar la cookie y el refresh token en el servidor.
Contadores y reactivos
Las librerías de datos estáticos (contadores.ts · 36 ítems, reactivos.ts · 13, parametrosCalidad.ts · 21) definen metadatos (nombre, unidad, límites norma). Los hooks los cruzan con los valores del API para generar el estado de alerta.
Roles y vistas diferenciadas
El objeto user.rol del contexto determina qué componentes se renderizan. El rol operario ve solo el panel PTAR (donut + tabla KPIs). El rol admin accede a todos los dashboards, reportes y panel de gestión de usuarios.

Etapa 1 — El usuario ingresa sus credenciales
La página LoginPage.tsx (src/features/auth/LoginPage.tsx) recoge el email y la contraseña en un formulario. Al hacer clic en "Ingresar", la función ptarClient.login() (src/services/ptarClient.ts) envía esos datos al servidor mediante una petición POST /api/auth/login. La contraseña nunca se guarda en el navegador — viaja por HTTPS cifrada en tránsito y llega al servidor solo para ser verificada una vez.
Etapa 2 — El servidor verifica la identidad
El backend ASP.NET Core (ptar-backend-dotnet/PtarApi/Features/Auth/AuthController.cs) recibe las credenciales y realiza varias comprobaciones en orden: primero aplica el rate limit (máx 10 intentos por minuto desde la misma IP), luego verifica si la cuenta está temporalmente bloqueada por intentos fallidos previos, y finalmente compara la contraseña con el hash BCrypt guardado en la base de datos MySQL. Si la contraseña no coincide, incrementa el contador de fallos. Si llega a 5 fallos consecutivos, la cuenta queda bloqueada 15 minutos automáticamente.
Etapa 3 — El servidor genera dos tokens y los manda como cookies seguras
Cuando las credenciales son correctas, el servidor crea dos tokens: un access token JWT (válido 8 horas, contiene la identidad y el rol del usuario) y un refresh token (válido 7 días, sirve para renovar el access token sin pedir la contraseña de nuevo). Ambos tokens se envían al navegador mediante cabeceras Set-Cookie con la bandera HttpOnly=true, lo que significa que JavaScript no puede leerlos — solo el navegador los almacena y los envía automáticamente en cada petición. En producción además se activan Secure=true (solo HTTPS) y SameSite=Strict (solo peticiones del mismo sitio).
Etapa 4 — El frontend recibe la sesión (sin ver el token)
El servidor devuelve en el cuerpo JSON solo los datos básicos del usuario: { id, name, role }. Eso es lo único que el contexto de autenticación (src/state/AuthContext.tsx) guarda en localStorage. El token JWT en sí nunca toca JavaScript — vive dentro de la cookie httpOnly que el navegador gestiona de forma invisible. Esto elimina el riesgo más común: que un script malicioso (ataque XSS) lea el token y lo robe.
Etapa 5 — Cada petición posterior lleva el token automáticamente
Cada vez que el frontend llama a la API (registrar un caudal, consultar calidad, ver dashboards...), la función doFetch() en src/services/ptarClient.ts usa credentials: 'include'. Esa opción le dice al navegador que incluya todas las cookies del dominio en la petición, incluida ptar_access_token. El servidor ASP.NET valida automáticamente esa cookie en cada request: verifica la firma criptográfica, el issuer, el audience y la expiración. Si algo falla, devuelve 401 Unauthorized.
Etapa 6 — Renovación automática cuando el access token expira (Refresh Token Rotation)
Cuando el access token caduca (a las 8 horas), el servidor devuelve un 401. El cliente detecta ese 401 en ptarClient.ts y automáticamente intenta renovar la sesión enviando POST /api/auth/refresh. El servidor lee la cookie ptar_refresh_token, busca su hash en la tabla ptar_refresh_tokens de MySQL, verifica que no esté revocado y que no haya expirado, y si todo está bien genera un par completamente nuevo de access + refresh token. El token viejo queda marcado como revoked=1 para que no pueda usarse de nuevo. Si el refresh también falló (por ejemplo, el usuario lleva 7 días sin usar la app), se ejecuta logout() y se redirige al login. El usuario promedio nunca nota este proceso — la sesión se renueva de fondo sin interrumpirlo.

📖 ¿Qué es un Hash? ¿Qué es BCrypt? ¿Por qué no guardar contraseñas en texto plano?
¿Qué es un hash?
Un hash es una función matemática de un solo sentido: toma una entrada (por ejemplo la contraseña "MiClave123") y produce una cadena fija de caracteres completamente diferente (por ejemplo "$2b$12$Kx7Rq..."). Lo más importante es que es imposible ir en sentido contrario: si alguien roba el hash, no puede recuperar la contraseña original. Además, si la contraseña cambia aunque sea una letra, el hash resultante es completamente diferente. En la app, nunca se almacena "MiClave123" en MySQL — solo se guarda el hash. Archivo relevante: ptar-backend-dotnet/PtarApi/Features/Auth/AuthController.cs:89 y ptar-backend/app/routes/auth.py:55.
¿Por qué BCrypt y no MD5 o SHA1?
MD5 y SHA1 son algoritmos de hash diseñados para ser rápidos, lo cual es muy malo para contraseñas: una GPU moderna puede calcular 10 mil millones de hashes MD5 por segundo, lo que permite a un atacante probar todas las combinaciones posibles en minutos. BCrypt fue diseñado específicamente para ser lento: con workFactor: 12 (configurado en AuthController.cs:266), calcular un solo hash tarda ~250 milisegundos. Para el usuario legítimo que hace login una vez, es imperceptible. Para un atacante que intenta millones de combinaciones, es inviable. Además BCrypt genera automáticamente un salt aleatorio por cada contraseña, lo que significa que dos usuarios con la misma contraseña tendrán hashes totalmente distintos en la base de datos.
¿Qué pasa cuando alguien intenta hacer login?
El usuario escribe su contraseña → el servidor busca el hash guardado en MySQL para ese email → usa BCrypt.Verify(passwordIngresado, hashGuardado) → BCrypt aplica internamente la misma función con el mismo salt y compara. Si coincide: login correcto. Si no: login fallido. En ningún momento el servidor "descifra" la contraseña — la verificación se hace comparando hashes, no textos planos. La comparación es además time-constant: tarda el mismo tiempo independientemente de cuántos caracteres coincidan, lo que previene ataques de temporización.

📖 ¿Qué es un JWT? ¿Cómo funciona en la PTAR? ¿Por qué usar cookies httpOnly?
¿Qué es un JWT (JSON Web Token)?
Un JWT es un documento digital firmado que el servidor entrega al usuario tras hacer login. Tiene tres partes separadas por puntos: el Header (dice qué algoritmo se usó para firmar), el Payload (contiene los datos del usuario: id, rol, cuándo expira) y la Signature (la firma criptográfica que garantiza que nadie modificó el contenido). En la PTAR el payload incluye sub (id del usuario), role (operario/encargado/admin), jti (un ID único para ese token), iss ("ptar-api") y exp (cuándo expira). Archivo de generación: ptar-backend-dotnet/PtarApi/Services/JwtService.cs:14-32.
¿Por qué el servidor no necesita consultar la base de datos en cada petición?
El JWT lleva toda la información necesaria dentro de sí mismo, firmada criptográficamente con el JWT_SECRET que solo conoce el servidor. Cuando llega una petición, el backend ASP.NET (Program.cs:43-52) simplemente verifica la firma matemáticamente — si alguien alteró aunque sea un carácter del token, la firma no coincide y la petición es rechazada con 401. Esto significa que el servidor puede confirmar en milisegundos la identidad y el rol del usuario sin hacer ninguna consulta a MySQL, lo que hace el sistema muy eficiente.
¿Qué es httpOnly y por qué es crítico para la seguridad?
Normalmente las apps guardan el JWT en localStorage. El problema: cualquier script JavaScript que se ejecute en la página (incluso uno inyectado por un atacante vía XSS) puede hacer localStorage.getItem('token') y robar la sesión. Al usar una cookie con HttpOnly=true (AuthController.cs:30-38), el navegador guarda el token internamente y lo envía automáticamente en cada request, pero lo bloquea completamente para JavaScript: document.cookie y cualquier código JS simplemente no pueden verlo. En la PTAR el localStorage solo guarda nombre y rol (datos no sensibles) — el token real vive en la cookie httpOnly, fuera del alcance de cualquier ataque XSS.
¿Qué es SameSite=Strict y para qué sirve?
Un ataque CSRF (Cross-Site Request Forgery) consiste en engañar al navegador del usuario para que envíe una petición a la PTAR desde otro sitio web (por ejemplo, el usuario visita una página maliciosa que en segundo plano intenta hacer un POST a ptar-app.vercel.app/api/...). Con SameSite=Strict (AuthController.cs:35) el navegador tiene instrucciones explícitas: no envíes esta cookie si la petición viene de otro dominio. El ataque CSRF falla porque sin la cookie el servidor devuelve 401. Esta protección solo se activa en producción; en desarrollo se usa SameSite=Lax para facilitar las pruebas locales.

📖 ¿Qué es un ataque de fuerza bruta? ¿Cómo lo bloquea la PTAR?
¿Qué es un ataque de fuerza bruta?
Un atacante intenta adivinar la contraseña de un usuario probando miles o millones de combinaciones automáticamente: 123456, password, permoda2024... Si el sistema no tiene protección, un programa puede probar 10.000 contraseñas por minuto sin ningún obstáculo. Es uno de los ataques más comunes y simples, y funciona especialmente bien cuando los usuarios tienen contraseñas débiles.
Account Lockout — Bloqueo por intentos fallidos (AuthController.cs:20-108)
La PTAR cuenta los intentos fallidos de contraseña por usuario. Después del 5.º intento fallido consecutivo, la cuenta queda bloqueada automáticamente durante 15 minutos, y el sistema guarda en MySQL la columna locked_until = NOW() + 15min. Cualquier intento de login durante ese período devuelve directamente un error con el tiempo restante: "Cuenta bloqueada. Intenta en 12 minuto(s)." Cuando el usuario finalmente hace login con éxito, el contador se resetea a cero (failed_attempts=0, locked_until=NULL). Todos estos eventos quedan registrados en los logs con el email y la IP del intento.
Rate Limiting — Límite de peticiones por IP (appsettings.json:28-75)
El rate limiting es una segunda capa de protección independiente del lockout. Mientras el lockout bloquea cuentas, el rate limiting bloquea IPs. Si desde la misma dirección IP llegan más de 10 peticiones de login en un minuto, el servidor deja de procesarlas y devuelve HTTP 429 Too Many Requests. Esto detiene los ataques distribuidos incluso antes de que lleguen a verificar contraseñas. Los límites están configurados de forma diferenciada: el endpoint de cambio de contraseña tiene un límite más estricto (5/min) porque es especialmente sensible, mientras que el límite global de la API es de 50 peticiones por segundo para evitar sobrecarga.
¿Por qué ambas capas juntas? — Defensa en profundidad
El lockout solo se activa cuando se prueba un usuario real con contraseña incorrecta. Un atacante podría intentar eludir el lockout distribuyendo los intentos entre muchas IPs (botnet). El rate limiting por IP bloquea eso. A su vez, el rate limiting por IP puede eludirse con miles de IPs diferentes, pero ahí el lockout garantiza que ninguna cuenta quede comprometida aunque se llegue a 5 intentos. Combinadas, ambas capas hacen que cualquier ataque de fuerza bruta sea inviable en la práctica.

📖 ¿Qué son los HTTP Security Headers y el CORS? ¿Por qué importan?
HTTP Security Headers — instrucciones del servidor al navegador (Program.cs:151-160)
Los security headers son instrucciones que el servidor incluye en cada respuesta HTTP para decirle al navegador cómo debe comportarse al mostrar la app. No protegen al servidor — protegen al usuario de que su navegador sea manipulado:
  • X-Frame-Options: DENY — impide que la app se cargue dentro de un <iframe> en otro sitio web. Previene clickjacking: un atacante no puede superponer un iframe invisible de la PTAR sobre otro sitio para robar clics del usuario.
  • X-Content-Type-Options: nosniff — el navegador no puede "adivinar" el tipo de un archivo. Sin esto, un atacante podría subir un archivo de imagen que en realidad sea JavaScript y el navegador lo ejecutaría.
  • Referrer-Policy: strict-origin-when-cross-origin — cuando el usuario navega desde la PTAR a otro sitio, el navegador no revela la URL completa de la que venía (que podría contener datos sensibles en la query string).
  • X-XSS-Protection: 1; mode=block — activa el filtro XSS incorporado en navegadores antiguos. En navegadores modernos es redundante con CSP, pero no hace daño tenerlo.
  • Permissions-Policy — declara explícitamente que la app no usará cámara, micrófono ni geolocalización. Bloquea que código inyectado active esos dispositivos.
CORS — ¿Quién puede hablar con el backend? (Program.cs:68-77)
CORS (Cross-Origin Resource Sharing) es el mecanismo que controla qué dominios pueden hacer peticiones a la API. Sin CORS restrictivo, cualquier sitio web del mundo podría hacer peticiones a /api/... en nombre del usuario. Con .WithOrigins(["http://localhost:5174", "https://ptar-app.vercel.app"]), solo esos dos orígenes están autorizados. Cualquier otro dominio recibirá un error de CORS bloqueado directamente por el navegador, antes de que la petición llegue a procesar ningún dato. La opción .AllowCredentials() es indispensable: sin ella el navegador no adjuntaría las cookies httpOnly en las peticiones, y toda la autenticación dejaría de funcionar.

Esto significa que cada registro de caudales, reactivos o calidad queda asociado permanentemente al operario que lo ingresó, con timestamp y dirección IP.
Eventos de seguridad con etiquetas específicas (AuthController.cs)
Los eventos críticos de autenticación tienen etiquetas estructuradas para facilitar búsquedas y alertas: [AUTH FAIL] cuando alguien ingresa un email que no existe o una contraseña incorrecta, [AUTH LOCK] cuando una cuenta queda bloqueada, [REFRESH] cuando se renueva un token, [AUTH] cuando se cambia una contraseña. Estas etiquetas permiten filtrar fácilmente en el sistema de logs: por ejemplo, si se detectan 50 entradas [AUTH FAIL] desde la misma IP en 5 minutos, es una señal clara de ataque de fuerza bruta. El logging incluye siempre la IP (ctx.Connection.RemoteIpAddress) para poder correlacionar con otros sistemas de seguridad de red.
Cambio de contraseña: por qué revocar todos los refresh tokens
Cuando un usuario cambia su contraseña (AuthController.cs:266), el sistema ejecuta inmediatamente un UPDATE ptar_refresh_tokens SET revoked=1 WHERE user_id=@UserId. Esto invalida todas las sesiones activas del usuario en todos sus dispositivos. La razón: si alguien robó la sesión del usuario (por ejemplo accedió a su teléfono o laptop), cambiar la contraseña debe cerrar esas sesiones robadas. Sin esta revocación, el atacante podría seguir usando el refresh token durante 7 días aunque la contraseña ya haya cambiado. Es el equivalente digital a cambiar la cerradura de una puerta: cambia tanto la llave como todas las copias en circulación.

1 · Arranque del servidor
Program.cs registra todos los servicios en el contenedor DI (DbContext, Dapper, JwtService, SharePointSyncService…), configura el pipeline de middleware y lanza Kestrel en el puerto configurado. EF Core auto-migra las tablas de seguridad si no existen.
2 · Request entra
El frontend llama al backend con credentials:'include'. La cookie ptar_access_token viaja automáticamente en el header Cookie. El servidor recibe la petición HTTP y la pasa por el pipeline de middlewares en orden.
3 · Pipeline de middleware
Cada request atraviesa en orden: RateLimit (bloquea si excede límite por IP) → CORS (valida origin) → SecurityHeaders (agrega headers de seguridad) → Authentication (valida y decodifica JWT de la cookie) → Authorization (verifica rol requerido) → AuditLog (registra mutaciones) → Controller.
4 · Controller y lógica
Cada feature tiene su propio controller inyectado vía DI. La lógica de lectura usa Dapper (queries raw sobre vistas SQL, más rápido para dashboards). Las operaciones de escritura y entidades de seguridad usan EF Core. El controller arma el DTO de respuesta y lo serializa a JSON.
5 · Consulta a MySQL
Dapper ejecuta el query contra la vista SQL correspondiente (ej. v_balance_hidrico para caudales, v_tabla_datos_1 para calidad). Las vistas pre-calculan agregados para que el backend solo lea resultados ya procesados. EF Core se usa para INSERT/UPDATE en tablas de usuarios y tokens.
6 · Respuesta al frontend
El controller retorna Ok(dto) → ASP.NET serializa a JSON → el middleware de seguridad inyecta los headers de respuesta → llega al frontend como application/json. En caso de error: 400 (validación), 401 (sin sesión), 403 (sin rol), 429 (rate limit), 500 (error interno).
🗄️ Cómo se manejan los datos
Dapper para lectura (dashboards)
Las consultas de los 10 módulos de datos usan Dapper directamente sobre vistas SQL. El patrón es: IDbConnectionFactory → abre conexión → QueryAsync<T> con el SQL de la vista. Resultado mapeado automáticamente al DTO de respuesta.
EF Core para escritura (seguridad)
Los registros de usuarios (ptar_users), refresh tokens (ptar_refresh_tokens) y auditoría (ptar_audit_log) se gestionan con EF Core. Permite migrations automáticas al arrancar y operaciones transaccionales seguras en login y cambio de contraseña.
Sincronización SharePoint → MySQL
SharePointSyncService (IHostedService) se activa al arrancar el servidor y cada N horas. Autentica con MSAL Device Code Flow contra Azure AD, lee la lista de mantenimientos de SharePoint con filtros OData y los upserta en la tabla ptar_mantenimientos de MySQL.
Generación de PDFs
ReportesController recopila datos de múltiples vistas SQL, los pasa a QuestPDF que construye el layout (tablas, KPIs, encabezado con logo) y retorna el stream directamente como application/pdf. No se almacenan en disco, se generan on-demand.

PtarApi.csproj Manifiesto del proyecto .NET Es el equivalente del package.json de Node. Define que el proyecto usa .NET 10, lista todos los paquetes NuGet instalados (Dapper, EF Core, QuestPDF, BCrypt, MSAL…) y sus versiones. Cuando corres dotnet restore, .NET lee este archivo y descarga lo que falta.
.gitignore Lista de exclusiones de Git Le dice a Git qué archivos ignorar: appsettings.Local.json (secretos), las carpetas bin/ y obj/ (compilaciones), y cualquier archivo temporal. Protege que secretos o binarios se suban accidentalmente al repositorio.

obj/
Archivos intermedios de compilación — caché interna que usa .NET para compilar más rápido en la segunda vez. No tiene utilidad directa. Se puede borrar sin problema (se vuelve a crear al compilar). Nunca va a Git.
